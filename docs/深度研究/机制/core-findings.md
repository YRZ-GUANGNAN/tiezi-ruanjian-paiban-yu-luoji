# 客户端内部机制：8.72.0 同版静态研究与 9.49.1 局部对照

更新于 2026-10-13。本报告研究与真机测试同版的安装包，说明页面背后的布局、列表复用、图像加载、事件与动画机制。这里的“内部机制”不是 Android 操作系统内核，也不包含服务端推荐算法。手机行为由主报告记录；本文全部新结论来自静态方法体或字段，不声称已观测这些具体方法在手机上执行。

## 1. 图集确实有原生分页、回收与状态链

8.72.0 的 `NoteDetailImageDisplayPresenter.x6()` 明确调用 `T7()`、`n7()`、`H7()`，分别进入列表配置、状态订阅与生命周期监听。`T7()` 使用 Android `RecyclerView` 与 `MultiTypeAdapter`，不是仅凭包内存在某个库推断的实现。

| 项目 | 8.72.0 代码中的默认分支 | 证据 |
|---|---|---|
| 排列与停靠 | 方向 0，即横向；挂接 `PagerSnapHelper` | K101、K111 |
| 项目复用 | `setItemViewCacheSize(3)` | K111 |
| 额外布局范围 | `m(100)` 保存为额外布局值，`getExtraLayoutSpace` 原样返回正值；这是布局空间 100 px，不是预加载 100 张图片 | K024、K111、K115 |
| 变更动画 | 关闭 `SimpleItemAnimator` 的 change animation；该 LayoutManager 不支持 predictive item animations | K111、K116 |
| 测量及嵌套 | `setHasFixedSize(true)`、`setNestedScrollingEnabled(false)` | K111 |
| 恢复图片索引 | 索引大于 0 时更新两个索引字段，再 `post` 一次列表定位回调 | K113 |
| 当前页与总数 | 单独维护当前索引，并生成“第几张、共几张”的无障碍文案 | K002、K103 |

`setHasFixedSize(true)` 是列表优化提示，不能解释为所有图片原始尺寸相同。缓存 3 项也不能解释为只下载三张图。图片网络缓存、解码缓存与 ViewHolder 缓存是不同层。

已有真机 R28–R47 的单页翻转、首尾停留，与上述分页设计相容；尚未证明该次真机必然走这一个 Presenter，包内还有 `AsyncImageGalleryController`。后者 `F4()` 使用 `DiffUtil.DiffResult.dispatchUpdatesTo` 增量更新适配器，并非整张图集必须重建。该并存路径单独记录，不与 v3 路径拼成未经证明的调用链。〔K009、K128〕

## 2. 图集高度有比例约束与设备分支

`C7()` 先判断一个设备/布局条件；条件为真时直接返回 `-1`。常规分支选择参考尺寸 W，再将 `NoteFeed.q0(0)` 的返回值 r 传入帮助方法，边界为 0.75 和 2.0。帮助方法确切执行：

```text
H = int(W / clamp(r, 0.75, 2.0))
```

`q8()` 将 H 写入图集列表高度，同时写入对应背景 `FrameLayout` 的高度，并请求布局更新。这样媒体区域和其背景同步变化。〔K113、K121、K141〕

边界必须保留：W 的来源还包含 `SDK_INT <= 33` 与设备条件，可能采用一个尺寸方法，或两个尺寸值的较小值；这些尺寸方法本轮没有继续展开，因此不能把 W 无条件等同于手机物理屏宽。r 的取值来自 `NoteFeed.q0(0)`，本轮没有展开该访问器，不能断言所有输入都直接取图片文件的宽高比。`-1` 对应 Android 布局的 MATCH_PARENT 值，但启用条件尚未恢复。复刻时应把媒体宽高约束做成可配置布局规则，结合真机像素测量，而不是把一个截图高度写死。

## 3. 页码动效存在完整的同版静态时序

可恢复的 8.72.0 默认链如下：

```text
RecyclerView 滚动状态 = 1（拖动），且图片数量 > 1
  → O7() 调用 u7()
  → 页码 alpha 到 1，200 ms，AccelerateInterpolator
  → 淡入结束回调 w7()
  → x7(5000)，先移除旧 Handler 任务，再设置延时
  → y7() 将 alpha 到 0，200 ms，AccelerateInterpolator
```

证据是 K122、K123、K130、K138、K102、K114。`y6()` 还移除 Handler 回调并取消页码控件持有的 Animation。〔K124〕

5000 ms 是从这个淡入结束回调安排的延迟，不是从手指按下或截图采集开始计时。其他调用、重复拖动、热补丁与主线程调度可能改变可见时间。早期 R31 五次截图只支持“数秒后隐藏”；本轮逐帧分析另在动效报告中提供约 195 ms 加速淡出的拟合，不能把拟合包装成精确测得源码常量或证明该方法必然被调用。该 200 ms 仅适用于这一页码透明度路径，不是整个 App 的统一转场时长。

## 4. 页面状态通过快照和变化流驱动

`il4.e` 包含以 `Class<?>` 为键的 `ConcurrentHashMap<Class<?>, Result<Object>>`，以及携带状态类型和结果的流。图集 `n7()` 为多种状态取当前值，随后组合变化来源；点赞控件 `x6()` 也采用这一形状。点赞点击本身被转换为事件并交给节点中的事件接收器，UI 的当前选择态由 `NoteFeed` 更新。〔K017、K112、K109、K120〕

9.49.1 对应代码去掉了部分混淆歧义：`Observable.concat(已有状态, 后续变化流).observeOn(...).subscribe(...)`，该结构在图集与点赞 Presenter 中都存在。〔N201、N206〕据此可支持“初始化时取得当前状态，后续由变化流更新”的客户端机制；不能进一步声称所有页面共用一个全局 Redux Store。

调度边界：8.72.0 可见 `n1(wb9.a.a())`；但调度器的初始化方法 K143 没有可用体，K136 仅转发到另一个函数。因此本轮不能把它命名为“已确认在 Android 主线程 observeOn”。状态具体含义、全局 Store 生命周期、订阅撤销最终责任、网络失败回滚顺序均未完整展开。

复刻建议是将“业务状态”和“按钮动画”拆开：同一笔记使用一个稳定的业务 ID，各页面订阅状态变化；视图复用时先从当前状态渲染，避免因页面重新进入而误播点赞动画。该建议不是恢复得到的服务端协议。

## 5. 图片加载包含尺寸、占位和实验分支

8.72.0 `NoteDetailPhotoNoteItemPresenter.e7()` 根据 `android_photonote_img_load_opt` 走两条分支：一条交给 `XYImageView.l()`；另一条用图片 URI、控件宽高与回调构建图像请求。方法体直接涉及 `com.facebook.imagepipeline.request`，所以对这个局部可确认存在 Facebook 图像管线调用，不只是库名存在。〔K117〕

`XYImageView.l()` 可按输入修改布局尺寸和边距，设置圆角/背景或占位相关 hierarchy 项，再建立 controller。`getSizedImageRequestBuilder()` 优先使用传入图像信息中的尺寸，缺失时取控件尺寸；两项都有值时附加尺寸参数，任一为 0 时退回不带尺寸参数的请求。该私有方法的调用者本轮未追到完整链，因此这证明控件提供该能力，不能保证每一图像请求都经过它。〔K125、K126〕

`S6()` 还给图片设置 `transitionName`，表明共享元素式导航有可用的命名锚点；这不能单独证明从首页点详情时一定执行共享元素转场。〔K118〕`setFadeDuration(int)` 接受外部时长，尚未恢复本场景的实际传入值，不能给所有图片入场规定一个“原版默认时长”。〔K127〕

9.49.1 对应 `db()` 改用 `NoteXYImageView`，有本地文件预览分支，以及在一个配置条件开启时检查 `isLaidOut()`：布局未完成则添加 `OnGlobalLayoutListener` 再执行加载回调。此处是方法级差异，不等于所有 9.49.1 图片必然延后加载。〔K201、K203〕

复刻建议：先测量媒体占位，再异步加载图片；用稳定 key 取消旧请求，复用时重置占位/错误/过渡状态；预览与远程资源分开处理。失败重试、渐进式图片、缓存大小、网络优先级和预取窗口仍缺完整证据。

## 6. 信息流的排版、回收和返回恢复

8.72.0 `ExploreView.C1()` 从注册的多类型 binder 找到某个笔记类型，并在配置分支中调度初始化任务。`D1()` 对该类型的共享回收池设置 `setMaxRecycledViews(type, 16)`，再赋给 RecyclerView。它不是“全 App 只缓存 16 个帖子”，也不是网络分页条数。〔K131、K140〕

`ExploreView.e3(list, Parcelable)` 将缓存列表中的笔记标记 `isFromCache`，恢复数据至 adapter，调用 `notifyDataSetChanged()`，随后用 `LayoutManager.onRestoreInstanceState(parcelable)` 恢复布局状态。它提供了列表内容和滚动布局同时恢复的真实代码路径，与此前部分返回位置实测相容，但没有追到所有返回入口的调用者。不能保证每个入口都恢复到完全相同像素。〔K132〕

`ExploreDoubleRowStaggeredDiverDecoration.getItemOffsets()` 对普通卡片使用列索引计算间隔：最左、最右边缘取配置间距 s，内部相邻边各取 `s >> 1`；满跨条目四边偏移为 0；顶部和底部还随条目类型、满跨位置、末行条件变化。〔K134〕这解释了双列卡片不能简单套用一组完全相同的外边距。s 的默认构造链本轮仅读到一个委托，实际数值没有恢复，不应编造“默认 8 dp/12 dp”；如 s 为奇数，两侧整数右移之和还会少 1 px。〔K139、K142〕

该瀑布流 LayoutManager 明确关闭 predictive item animations。关闭某类列表动画并不等于关闭所有页面动效。〔K135〕

9.49.1 的 `FeedCustomMultiTypeAdapter.onBindViewHolder()` 延续 `MultiTypeAdapter` 绑定并加入计数/条件日志；`onViewRecycled()` 委托相应 binder 回收。出现 `>100` 的分支属于绑定计数及后续上报条件，不能拿它当缓存、分页或预加载上限。〔K202、K204、K205〕8.72.0 找不到这个完全同名类，不能据此断言旧版没有对应功能。

## 7. 请求、分页与“内核”的可见边界

8.72.0 `ExploreService` 有多个首页请求变体，返回列表；9.49.1 接口方法与参数形状发生变化。`ExploreView.M2()` 可见刷新来源、频道标识、缓存/已有列表上下文及请求协调器的调用，但该方法包含多处 JADX 重复代码警告。没有恢复请求参数映射、响应消费和完整去重逻辑，不能从它推导固定分页条数、刷新是否清空全部旧数据，或真实推荐排序。〔K013、K137、N107〕

9.49.1 的关注流响应字段有 `cursor`、`hasMore`。这只适用于这个版本这个模型，不能无证据推广到发现、搜索和 8.72.0 的所有列表。8.72.0 对应同名模型选择器没有找到，保留为未解。〔N106；K022/K023 为失败记录〕

本轮有直接方法体支持的渲染机制是 Android Views、RecyclerView、多类型 adapter、图像管线、Lottie/属性动画、状态流。此前资源研究发现 RN/Hermes 等打包组件，只能说明安装包具备混合技术；尚未把某一真实页面归属到 RN 或 WebView。没有解码播放器 `.so`，未恢复 JNI/native 调用，也未观测运行时加载库、服务端策略或推荐模型。

几乎所有关键方法都先经过 `PatchProxy`。本文描述的是打包默认分支；远程补丁、功能实验、资源配置、机型条件可能让实际行为偏离静态默认，复刻验收仍应以选定版本的真机行为为准。
