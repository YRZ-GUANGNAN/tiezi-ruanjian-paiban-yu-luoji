# 渲染管线与帧采样：能确认什么

设备为魅族 21，Android 16 / API 36，小红书 8.72.0 / 8720916。屏幕 1080×2340，440 dpi，字体缩放与三种系统动画倍率均为 1.0。原始环境读数的派生副本见 [environment.json](environment.json)。这里研究客户端页面绘制，不涉及 Android 操作系统内核。

## 当前绘制路径

T00 和四次转场前后的 `gfxinfo` 均报告 **Pipeline=Skia (Vulkan)**。结合窗口和方法证据，可确认所采页面包含 Android View/HWUI 绘制路径；这不能说明整个 App 全部页面都使用同一实现，也不能将视频解码与界面绘制视为一件事。

| 场景 | 运行记录 | 可作出的判断 |
|---|---|---|
| 首页 | `IndexActivityV2` 窗口 | 存在首页原生窗口统计 |
| 图文进入 T02 | 新增 `NoteDetailActivity` 窗口 | 该次详情进入建立独立窗口；不是只由卡片尺寸猜测页面结构 |
| 图文退出 T03 | 详情窗口不在事后快照中 | 返回后无法再从该窗口读取完整退出帧 |
| 视频详情 | `DetailFeedActivity`，同时记录 TextureView/SurfaceTexture | 视频表面与普通 UI 统计并存；不能由此指定解码器或码率策略 |
| 评论展开 T05 | 同一 Activity 名下新增一组不同 `Stats since` 的窗口记录 | 确实出现独立的窗口统计块；仅凭名称无法确定 Dialog/Popup 的具体类 |
| 评论关闭 T06 | 上述新增窗口不在事后快照中 | 关闭时序需靠录屏判断，不能以其缺失推算动画帧率 |

运行记录中的 HWND/内存地址与设备真实 serial 不导出。安装包里 RN/Hermes 等组件的存在仍不能证明某个已测页面正在走这些技术；方法证据见[内部机制报告](../机制/core-findings.md)。

## 为什么没有给出“转场掉帧率”

已按 `Window + StatsSince + IntendedVsync` 对每次前后快照做差，只保留前次采样之后、Flags=0 且完成时间有效的记录。结果见 [gfx-delta.json](gfx-delta.json)，不是直接抄进程累计比例。

| 录屏 | 两次快照间隔 | 新帧采样情况 | 解释边界 |
|---|---:|---|---|
| T02 详情进入 | 11.797 秒 | 首页 1 条有效；新详情窗口 14 条中 13 条有效 | 新窗口没有同生命周期的前表，区间还含加载与采样开销 |
| T03 详情退出 | 11.647 秒 | 首页新行 1 条但被 Flags/时间检查排除；详情窗口已消失 | 不具备完整退出帧序列 |
| T05 评论展开 | 12.032 秒 | 视频窗口累计新增 684 帧，只留下最近 120 条；新窗口 13 条中 11 条有效 | 视频窗口仅保存末尾约 1.982 秒，动画早已结束 |
| T06 评论收起 | 12.280 秒 | 视频窗口累计新增 769 帧，只留下最近 120 条 | 仅保存末尾约 1.981 秒，评论窗口已消失 |

例如 T05 最近 120 条的 `FrameCompleted−IntendedVsync` 中位数为 3.7932ms、P95 为 4.7899ms。这是录屏末尾的框架采样，不能称为评论开启动画的性能。累计 Janky 差值也只能描述整个采样区间，不能作为特定动画的掉帧率。

录屏本身采用可变帧间隔，页面静止时可不连续编码。局部约 8.3ms 的帧间隔、整个文件的平均编码帧率、HWUI 绘制帧、视频解码帧和屏幕最终呈现帧，不能互相替代。

## 对独立实现的意义

列表复用、图片解码/请求、视频表面、属性动画和页面导航应分别测量。自研验收使用固定素材与同一动画倍率，先验证位置与时间，再用覆盖完整动作的系统帧时间线验证性能。后续若继续性能研究，应在动画发生期间采集完整时间线并同步输入事件，避免长时间等待后才读取最近帧。

本轮没有恢复播放器 native 内部、完整图片缓存策略、JNI 调用或服务端推荐逻辑；这些不能从上述管线名称推导出来。
