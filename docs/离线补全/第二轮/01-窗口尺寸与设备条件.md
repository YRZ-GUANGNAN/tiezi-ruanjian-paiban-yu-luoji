# 图集窗口尺寸与设备条件

本报告针对 8.72.0 的打包默认分支，补充[上一轮适配追踪](../02-设备适配静态追踪.md)。所有静态来源身份见[证据索引](evidence-index.json)，运行现象另见[模拟器报告](03-模拟器宽度与返回观察.md)。

## W 和 r 已定位

此前 K121 中的短类名 `o1` 有 45 个候选。本轮从 DEX 的实际调用指令确定为 `q68.o1`，随后用 REA 展开其方法，未按名字相似度猜测。精确符号及 code-unit offset 见 [W100 调用引用](auxiliary/W100-C7-dex-references.txt)。

| 入口 | 实际静态来源 | 证据 |
|---|---|---|
| `q68.o1.h(context)` | `Resources.getDisplayMetrics().widthPixels` | [W104](evidence/W104-q68-o1-h.java.txt) |
| `q68.o1.f(context)` | SDK ≥ 30：当前窗口 `WindowMetrics.bounds.width()`；旧系统：`getDefaultDisplay().getSize(Point).x` | [W102](evidence/W102-q68-o1-f.java.txt) |
| `q68.o1.e(context)` | SDK ≥ 30：当前窗口 `WindowMetrics.bounds.height()`；旧系统：`Point.y` | [W103](evidence/W103-q68-o1-e.java.txt) |
| `NoteFeed.q0(0)` | `imageList[0].getWidth() * 1.0f / getHeight()`；空列表返回 0 | [W106](evidence/W106-note-feed-q0.java.txt) |
| `ImageBean` 的宽高 getter | 直接返回 `width` / `height` 字段，不在这里解码测量图片 | [W110](evidence/W110-image-bean-width.java.txt) · [W111](evidence/W111-image-bean-height.java.txt) |

结合既有 [K121 高度入口](../../深度研究/机制/raw/K121-image-height.java.txt) 与 [K141 比例限制](../../深度研究/机制/raw/K141-gallery-height-formula.java.txt)，正常有限正数比例时为：

```text
if ro.m.c():
    return -1

if so.c.p() || SDK_INT <= 33:
    W = resources.displayMetrics.widthPixels
else:
    W = min(currentWindowBounds.width, currentWindowBounds.height)

r = imageList[0].width * 1.0f / imageList[0].height
H = int(W / clamp(r, 0.75, 2.0))
```

这里 W 是像素量。Android 14+ 对应分支使用当前窗口 bounds，不是硬编码手机型号尺寸；这些方法没有显式扣除 `WindowInsets`，也不读取图集 View 的 measuredWidth。不能把窗口 bounds、物理面板尺寸和去除系统栏后的内容区混为一谈。

`-1` 是布局参数 `MATCH_PARENT`，实际填满范围由父容器决定。图片字段填充、旋转与裁切语义尚未恢复；不能把字段比例直接称为已抓取的服务器原图比例。空列表的 0 会进入 0.75 下限分支，但 0/0、NaN 等异常数据能否进入此处仍未知。

## 特殊布局不只是尺寸公式

上一轮已确认 `ro.m` 初始化时把 `so.c.p() || so.c.n()` 存入布尔字段；本轮补出以下链路。

| 条件 | 新增直接证据 | 结论边界 |
|---|---|---|
| `so.c.n()` | [A010](evidence/A010-fold-condition.java.txt)：`f() || s()`；[A013](evidence/A013-special-condition-s.java.txt)：`s() → g()` | 是两个条件的或；A010 文件名中的 fold 只是采集标签，本轮未证明整个条件专指折叠屏 |
| `f()` 与 `g()` | [A012](evidence/A012-special-condition-f.java.txt)、[A018](evidence/A018-special-condition-g.java.txt) 读取两个 Lazy 值；[A011](evidence/A011-device-category-initializer.java.txt) 绑定对应初始化器 | 读取时机与重新计算不能从方法名推断 |
| 两个初始化器 | [A022](evidence/A022-special-lambda-b1.java.txt)、[A024](evidence/A024-special-lambda-c1.java.txt)：分别查询 `xo.a.c().a()` / `.b()` 的 `contains(so.c.b())` | 存在按机型键匹配的两个名单；名单内容、下发来源和业务类别尚未展开 |
| 匹配键 `so.c.b()` | [A026](evidence/A026-device-list-key.java.txt)：取 `Build.MODEL`，以忽略大小写的 `Build.MANUFACTURER` 正则替换，再 trim；MODEL 空时为 `unknown` | 不能当成精确、完整的品牌兼容表；也未验证所有输入下的正则含义 |
| `so.c.c()` 的 Lazy 来源 | [A020](evidence/A020-category-property-invoke.java.txt)：通过未展开的 `j.k().r(...)` 读取 `key_device_type_from_cloud`，默认值为 `u() ? "pad" : "phone"` | 键名不是网络抓包证据；未核实读取层、当前值和远端覆盖 |
| `u()` 的默认分类 | [A025](evidence/A025-default-pad-condition.java.txt)：`v() || w()` | 后续两条只说明默认分类分支 |
| `v()` | [A027](evidence/A027-default-pad-v.java.txt)：若 `s()` 为真返回假；否则比较尺寸估计是否落在 `[8.4, 19.0]` | 不是全部平板或大屏判定规则 |
| 尺寸估计 | [A029](evidence/A029-device-measurement.java.txt)：从 `d(context)` 的 Point 与 `xdpi/ydpi` 求对角长度，横屏时先交换 x/y | 属于基于报告像素密度的英寸估计，Point 获取帮助器尚未展开，不是实测物理尺寸 |
| `w()` | [A028](evidence/A028-default-pad-w.java.txt)：查询 `ro.build.characteristics` 并检查小写结果包含 `tablet` | 属性访问帮助器未展开，未实测设备属性 |

`so.c.p()` 还要求 `k84.c.a()`。上一轮看到该方法先判断 `L()`；本轮 [A015](evidence/A015-gate-L.java.txt) 证明 `L()` 的未补丁默认返回 false。因此没有任何相关热补丁覆盖时，该 gate 的第一分支允许通过。不能将后续 `Q()` 和字段命名成已验证的实验开关；[A016](evidence/A016-gate-Q.java.txt) 只确认它返回一个布尔字段。

这些方法多数带 `PatchProxy` 早退。初始化布尔字段的读取与后续重新调用 `p()` 不是同一个时点，不能为了简化公式随意合并。

## 本轮能解决什么

现在有证据支持“窗口尺寸 + 图片记录比例 + 设备类别/名单条件”共同决定这条布局路径。既不是随机生成机型参数，也不是仅凭一台手机截图还原出所有设备规则。

剩余重点为：名单与读取配置的实际值、设备尺寸 Point 的来源、图片字段填充及后续切图是否重算。模拟器已观察到动态改宽后容器高度可能保留旧值，不能因静态公式完整就断言每次配置变化都会调用它。

A017、A021 返回未提供方法体，成功读取的对应实现另存为 A020、A022；索引保留查询状态，不把空方法结果误算为完整源码。
