## 从图集入口看实际计算顺序

已保存的 [K121 高度入口](../深度研究/机制/raw/K121-image-height.java.txt)在未命中 `PatchProxy` 的路径中先执行特殊条件，再选择参考尺寸 W。按原顺序整理如下；`o1` 保留反编译片段中的简称，尚未确认完整类名：

```text
if ro.m.c():
    return -1

if so.c.p() || SDK_INT <= 33:
    W = o1.h(context)
else:
    W = min(o1.f(context), o1.e(context))

r = NoteFeed.q0(0)
H = int(W / clamp(r, 0.75, 2.0))
```

最后一行由 [K141 比例夹取方法](../深度研究/机制/raw/K141-gallery-height-formula.java.txt)支持。`-1` 对应 Android 布局的 `MATCH_PARENT` 值，但不应直接翻译成“全屏”：实际填满多大的父容器仍取决于父级布局。媒体列表与背景高度同步的既有证据见[机制报告](../深度研究/机制/core-findings.md)。

W 在这里仅称为“参考尺寸”，不能预先认定为物理屏宽、窗口宽度或扣除安全区后的内容宽度。r 来自 `NoteFeed.q0(0)`，该访问器未展开，不能断言始终等于图片文件的宽高比。

## 新补出的条件链

| 方法 | 本轮直接看到的代码 | 可以下的结论 | 仍未知 |
|---|---|---|---|
| `ro.m.c()` | 返回 `f288794b` | 图集的特殊条件先读取一个布尔字段 | 所有写入位置与字段生命周期 |
| `ro.m.<clinit>` | `f288794b = so.c.p() || so.c.n()` | 初始化时由两个判断的或结果赋值 | `so.c.n()` 的含义，之后是否修改字段 |
| `so.c.p()` | `so.c.c() == "pad" && k84.c.a()` | 默认分支既检查字符串 `pad`，也要求另一布尔条件 | `pad` 的判定来源、是否覆盖全部平板设备 |
| `so.c.c()` | 从 `f301392d.getValue()` 取得字符串 | 类别值在本方法中通过 Lazy 字段获取 | Lazy 初始化计算、读取了哪些系统字段 |
| `k84.c.a()` | `!L()` 时真；否则 `Q()` 时假；否则检查 `f212604d == "test"` | `pad` 分支还受多条件约束 | L/Q 和字段的业务含义，不能擅自命名为生产、实验或用户设置开关 |

`so.c.p()`、`so.c.c()`、`k84.c.a()` 的方法中可见 `PatchProxy` 优先分支。本报告讨论的是没有由该分支替换结果时的静态逻辑，没有验证设备实际命中情况。`ro.m.c()` 读取初始化字段，而稍后的 W 选择重新调用 `so.c.p()`；不能无证据把两次条件合并或删掉后者。

因此，旧报告里的“存在设备/布局特殊条件”现在可具体追到上述初始化和类别判断，但仍不能改成“所有平板或折叠屏都走 MATCH_PARENT”。尤其没有得到 `so.c.n()` 的语义，也没有恢复按品牌/型号逐项匹配的规则。

## 字体只能保留局部结论

已有 [K109](../深度研究/机制/raw/K109-like-attach.java.txt)显示 8.72.0 的 `NoteDetailLikeBtnPresenter` 对一个 `BtnViewCustomTextView` 设置 `Typeface.defaultFromStyle(1)`，这是该控件的默认粗体样式设置；同时另行设置文本颜色。它没有给出帖子正文、标题或评论的精确字号，也不能证明全 App 使用相同字体。

9.49.1 的对应局部 [N206](../深度研究/机制/raw/N206-like-bind.java.txt)调用 `j.f(XYUtilsCenter.f(), 1)` 获得字体对象后设置到控件，再设置颜色；帮助方法未展开，不能把参数 `1` 无条件解释成与旧版相同的默认粗体实现。旧版和新版的局部调用差异应保留，不能由此恢复正文的字体族、字重数值、字号或行距。截图文字框和光栅读数仍只采用[排版量化报告](../深度研究/排版/layout-findings.md)中的有限解释。

## 对独立实现的实际帮助

现在可以把“媒体高度策略”设计成独立模块：输入参考尺寸、比例和明确的特殊布局策略，输出媒体及背景高度；将设备分类与布局计算分开，便于之后替换证据不足的条件。这是自研建议，模块的字段和接口并不是从原 App 恢复出的设计。

目前还不能照搬一套覆盖所有手机的规则。需要继续明确 W/r 的来源、`o1` 的实际类、特殊条件的剩余分支，随后用目标设备验证不同窗口、安全区、字体缩放、导航方式与横竖屏的结果。模拟器可以先覆盖可控的窗口和字体条件，但不能替代各厂商真机的最终验证。
