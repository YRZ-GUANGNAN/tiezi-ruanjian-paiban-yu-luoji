# 第四轮：评论适配与图片呈现

本轮补齐了普通评论的测量宽度来源、图片评论的尺寸缓存、数量角标及默认裁切/圆角。另一项重要结果是排除相似名称造成的误用：**目前仍不能给普通长评论填写固定折叠阈值。**

研究对象仍为 Android **8.72.0 / 8720916**，仅非购物功能。本轮没有操作真机或模拟器，没有开发软件，也没有将静态规则写成新版实测结果。

## 对后续独立实现最有用的增量

- 评论尾部换行有两种测量宽度：当前正文控件宽度，或资源宽度减 110.5/135.5dp 的缓存值。两个分支的 100px 兜底条件不同。
- 多图缩略图的参考宽来自 `Display.getRealSize`，经 Lazy 和类初始化缓存；不是每个图片控件即时宽度。动态改宽是否刷新仍待测。
- 只显示首图需要设备条件与配置共同成立；已定位配置键及调用默认值，但当前配置值未知。
- 图片角标显示总数“共 N 张”，不是剩余数；XML“共9张”也不是图片数量上限。
- 所选布局的图片默认圆角为 **6dp**，数量角标背景圆角为 **16dp**；布局与在线/本地加载入口均指向居中裁切。最终像素与主题覆盖尚未实测。
- “展开全文”资源目前的直接消费者属于视频笔记正文，两个 fold 配置键的直接消费者通向 Alpha 聊天分支；翻译切换也不能当作正文展开。

## 适配不能只用一个“屏幕宽度”

| 使用位置 | 本轮恢复的参考量 | 缓存/更新边界 |
|---|---|---|
| 评论尾部换行，设备条件分支 | 正文控件 `getWidth()`，至少 100px | 调用时读取 |
| 评论尾部换行，另一分支 | Context 资源宽度减固定留白；非正值才退到 100px | 当前 Presenter 的 Lazy |
| 多图缩略图方块 | Display 返回的宽度，减 155dp 后除以 3 | 宽度 Lazy＋控件类初始化 |

这些都是静态来源关系；不等于已证明所有机型、窗口变化和进程恢复正确。尤其不能将测量公式计算值替换掉此前截图/层级的实际几何。

## 核验与收录取舍

精选公开 **37 份同版 REA Evidence**，其中 30 次方法查询，28 个提供方法体、2 个未提供；另有 **18 份独立辅助解析**和 2 份条件表。两个无体构造结果的关键 Lazy 绑定由原始 DEX 辅助核对，没有将辅助结果冒称 REA 方法体。

宽度浮点常量、判断分支、4 份图片布局的属性对、资源索引、裁切对象标识、圆角数组、数量文字和背景均做了源材料交叉检查。文字规则还完成独立只读复核。33 个重复导航、无关分支或失败/部分结果留在本地，不为增加数量导入；完整类名搜索和 LivePhotoTag 不作为本轮结论。

新增运行观察为 **0**，未重新处理旧真机原始观察。文档只引用第三轮已发布的两项评论宽度作计算量与观测量的区别说明。原 **84 项几何、77 份机制证据、28 项参数、31 部分 / 69 待测 / 0 完整**保持原口径。

长评论是否折叠及如何恢复、当前配置值、主题覆盖、实际裁切像素、图片缓存刷新与旧/新控件路由仍待验证。本轮研究不声称覆盖整个小红书；原始 APK、页面层级和用户内容没有公开。
