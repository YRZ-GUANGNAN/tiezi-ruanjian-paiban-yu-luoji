# 真实 8 图评论：槽位、查看器与异常边界

本轮在帖子 A、C 的有限评论范围查找，A 另展开过一个回复列表。不是全文抓取或穷尽搜索；只浏览现有内容，没有为研究发图片。具体范围在 [searchBoundary](observations.json)。

## M1 确实不是单张拼图

帖子 C 的同一条评论 M1，在 E128 有三个独立 `ImageView` 图片节点，画面也显示不同的图片内容。

| 观察 | 动作 | 查看器显示 |
|---|---|---|
| E129 | 点第一个图片区域 | 1/8 |
| E130 | 在查看器中向左滑动 | 2/8 |
| E132 | 返回列表后，点第三个图片的可见区域 | 3/8 |

这支持“本条评论的查看器报告总数为8，第一/第三槽映射到第一/第三页”。没有读取源图片数组或网络响应，也没有依次打开全部8页；不能将显示计数等同于已验证全部原图可加载。

E128/E131/E133 的完整 XML 摘要相同，说明这两次看图返回后恢复了该记录的层级与位置。背景视频变化，截图不相同。

## 当前不是正常三列基线

1080 宽、280dpi 的 E128 报告以下节点边界，图片纵向完整可视，但右侧排版异常：

| 槽位 | XML 报告的边界 `[left,top,right,bottom]` | 报告范围大小 px | 解释限制 |
|---|---|---|---|
| 1 | [100,730,649,1279] | 549×549 | 第一槽完整方形；不能当手机端通用默认尺寸 |
| 2 | [660,730,986,1279] | 326×549 | 横向被裁切，不能把326当真实完整View宽 |
| 3 | [829,730,986,1279] | 157×549 | 与第二槽报告范围重叠，且横向被裁切 |

第一槽右边与第二槽左边相差11px，只是这一对报告边界的间隔。第三槽不是第二槽右侧的等距排列；不能据此建立正常三列规则。

截图可见过大的图像、重叠及延伸到正文区域之外的图像内容。XML 的可访问性边界与实际绘制范围也不完全等同。只记录原始报告值，不把裁切范围包装成三张图真实宽度。

此时进程已经经历过第五轮和本轮显示变化，并非干净启动基线。第四轮的[静态图片条件表](../../离线补全/第四轮/02-图片评论尺寸裁切与角标.md)不能单独证明这次用了哪个 View、哪个宽度缓存或哪个运行开关；本轮没有新增静态分析来解释549px。

## 同一样本动态改宽：无效边界不能当尺寸

E133 → E134 只把1080宽改为720宽，密度、系统字号、进程不变。M1 的图片节点仍有三个：

| 节点 | E134 报告边界 | 可否用于计算完整图片尺寸 |
|---|---|---|
| 1 | [100,730,626,1279] | 否，横向范围被裁切；高度仍为549px |
| 2 | [637,730,626,1279] | 否，right小于left，是无效横向范围 |
| 3 | [637,730,626,1279] | 否，同上 |

截图仍露出其他图片内容。不能因只有一个正宽矩形就写成“只剩一个图片节点”或“切换成只首图模式”，更不能把算出的负11当成真实图片宽度。导出保留反向坐标，并标注 `validReportedRectangle=false`，不擅自修正原件。

E135 恢复1080后，完整 XML 摘要与 E128 相同，说明恢复了原来的**异常**几何状态，不代表布局被修复。

## 已补到与仍缺的内容

- 已补到一个“查看器总数8、三个独立槽位、不同槽位对应不同页码”的真实样本。
- 未确认列表里的“共8张”角标。当前第三槽重叠裁切，因此“未观察到”不证明角标不存在或被配置关闭。
- 精确2张、3张、4张样本仍不足；不能用本条总数8替代全部组合。
- 正常未裁切多图尺寸、全部槽间距、角标像素、动态改宽后的面板/详情重建和新进程基线仍待测。

后续优先复用 M1 这个已固定的样本做干净生命周期对照，再补2/3/4张，价值高于继续无目的翻页。549px只进入异常记录，**不进入通用复刻参数表**。
